# 一、应用工具篇（补遗二期）

### **LangGraph 状态图编排框架（LangGraph）：**

LangGraph 是 LangChain 团队推出的智能体编排框架，专门用来搭建有状态、可循环的 Agent 工作流。它把一个任务流程画成一张图：每个节点是一步操作（调模型、调工具、人工确认），边决定下一步往哪走，流程还能在节点之间回头重试。和一次写死的线性链条不同，它自带状态管理与检查点，长流程跑到一半失败了，能从断点续上，不用从头再来。适合多步骤、有分支、要人工介入的办事型流程；小像就用 Coze + LangGraph 编排 6 大工作流，请假审批这类流程被拆成收集信息、查余额、预填单据、主管确认、提交等节点逐步执行。注意事项：图不是画得越复杂越好，节点和分支一多，调试与排障成本陡增；PM 要先把流程和异常分支在纸上画清楚再让工程建图，并给每个节点定好失败时的去向。

### **LangChain 应用开发框架（LangChain）：**

LangChain 是目前使用最广的大模型应用开发框架之一，它把调模型、拼提示词、接工具、查知识库这些常用动作，封装成可以拼装的组件。它的核心思路是「链」：把多个步骤按顺序串起来，上一步的输出喂给下一步，复杂应用就是一条条链的组合。后来居上的 LangGraph 出自同一团队，专攻有状态的图编排，两者常被放在一起比较和选型。PM 评审技术方案时，听到团队说用 LangChain，重点是问清它承担哪一段：是快速验证的原型，还是要长期维护的生产链路，两种用法对稳定性和可维护性的要求完全不同。注意事项：框架版本迭代快、抽象层多，好处是开发快，代价是排障时要穿透框架看底层调用；不要把「用了框架」当成架构设计本身，流程、兜底和评测仍要自己设计。

### **Dify 低代码开发平台（Dify）：**

Dify 是一个开源的低代码大模型应用开发平台，把提示词编排、知识库、工作流、模型接入都做成可视化界面，不写代码或少写代码就能搭出一个 AI 应用。它和 Coze 属于同一类工具：降低搭建门槛，让产品和运营也能参与调提示词、换模型、改流程。搭好的应用可以直接发布成网页，也可以经接口给其他系统调用，并支持私有化部署。PM 最该拿它做两件事：一是快速搭原型验证场景，几天就能拿真实流程给用户试；二是中小团队的内部工具（制度问答、工单助手）直接用它上线，省去从零开发的周期。注意事项：低代码不等于没门槛，复杂分支、精细权限与异常处理仍可能撞上平台的能力边界；选型时先拿最复杂的那个流程试搭，能跑通再定，别被演示里的简单场景带偏。

### **LlamaIndex 数据框架（LlamaIndex）：**

LlamaIndex 是一个专攻「数据接入」的大模型应用框架，解决的是怎么把企业自己的文档、数据库、接口数据整理好，再喂给模型使用。它提供现成的数据加载、切分、索引和查询组件，是搭 RAG 系统时最常用的工具之一，与 LangChain 是同类竞品。可以把它理解为站在数据一侧的框架：LangChain 更偏流程编排，它更偏让数据变得可检索、可溯源。当团队的痛点是文档格式杂、来源多、更新频繁时，PM 要意识到这属于数据工程问题，这类框架的价值就在这里；评估 RAG 方案时，值得问一句数据接入层是用什么搭的。注意事项：框架只解决管道，解决不了数据质量——源文档本身过期、冲突、没人维护，索引做得再好，答出来的也是错的，知识库的运营责任仍在业务侧。

### **多智能体开发框架（CrewAI & AutoGen）：**

当一个智能体忙不过来，常见做法是把任务拆给多个各有分工的智能体协作完成，这类框架就是为这种协作提供脚手架的。CrewAI 的思路像组建一个剧组：给每个智能体定角色、目标和工具，再按流程把任务交接下去；AutoGen 出自微软研究团队，更强调智能体之间用对话来协商和推进任务。两者都是开源框架，代表了多智能体落地的两种典型组织方式。PM 听到方案里要上多智能体，先问值不值：任务能不能由单个智能体加工具干完，能干完就别拆；真要拆，先定清每个智能体的职责边界和交接标准，再谈选哪个框架。注意事项：智能体一多，调用次数、延迟和出错点成倍涨，还可能出现互相推诿、循环对话的问题；必须设总轮次上限和人工兜底，并用评测证明多智能体确实比单智能体强。

### **推理部署工具（vLLM & Ollama）：**

模型训练完只是半成品，要让它对外提供问答服务，还需要一个推理引擎负责高效地跑模型，这类工具干的就是这件事。vLLM 是目前主流的开源推理引擎，靠分页注意力等机制把显存用得很省，能在同样的硬件上同时服务更多用户，多用于正式上线部署。Ollama 则主打简单：在自己电脑上一条命令就能把开源模型跑起来对话，是本地体验和验证模型的常用工具。PM 做私有化部署或成本测算时会碰到它们：同一块显卡能扛多少并发、延迟多少，很大程度上取决于推理引擎；想在本地验证模型效果时，先用 Ollama 把模型拉起来试，比看参数表直观得多。注意事项：推理引擎解决的是跑得快、跑得省，不改变模型本身的能力上限；选型时要把引擎、硬件、并发目标放在一起实测，别拿单用户演示的流畅度去推断上线表现。

# 二、技术术语篇（补遗二期）

### **ReAct 推理行动范式（ReAct）：**

ReAct 是智能体最经典的工作范式，名字来自 Reasoning（推理）加 Acting（行动）：让模型边想边做，而不是一次想完再做。它的循环是三步：先说出当前想法（想），再决定调用哪个工具（做），然后看工具返回的结果（观察），据此想下一步，如此往复直到完成任务。现在绝大多数 Agent 框架的底层循环，都是这个范式的变体。PM 设计 Agent 时，要把这个循环当成产品结构来设计：每一步的思考要不要展示给用户、工具失败时是重试还是换路、循环多少次必须停下来转人工，都要预先定好。注意事项：循环给了模型纠错的机会，也给了它绕圈子的机会——可能反复调同一个工具，或被错误的中间结果带偏；必须设最大步数、留全程日志，出了问题能回放是哪一步想歪的。

### **规划与反思（Planning & Reflection）：**

规划与反思，是让智能体从「走一步看一步」升级为「先谋后动」的两个机制。规划指动手前先把大任务拆成子任务清单，排出顺序和依赖，做的时候按单推进；反思指做完一步或拿到结果后，先自查对不对、偏没偏，再决定继续、修正还是重来。两者常配合使用：规划管全局路线，反思管每一步的质量。适合长任务和多步骤办事场景：先列出办一件事要查什么、填什么、找谁确认，再逐步执行、每步核对；PM 要决定的是反思的成本花在哪里，关键步骤步步反思，低风险步骤直接过。注意事项：规划和反思都要额外消耗调用次数和时间，任务越简单越不划算；还要防止模型对自己的错误答案「反思」后仍自信通过，关键结论的校验要靠规则和外部数据，不能只靠模型自查。

### **机器学习总览（Machine Learning）：**

机器学习是让计算机从数据里自己总结规律、而不是靠人把规则一条条写死的技术总称，深度学习、大模型都是它的分支。按学习方式主要分三类：监督学习用带答案的数据学规律（如拿标注好的工单学分类），无监督学习不给答案、让模型自己找结构（如把用户自动聚成几群），半监督学习介于两者之间，用少量标注带动大量未标注数据。大模型预训练用的自监督，可以看作监督学习的一种特殊形态。PM 判断一个需求该用什么方法时，先分清它属于哪一类：有历史标注数据的多半是监督学习，想从杂乱数据里找规律的属于无监督；分清类别，才知道要准备什么样的数据、怎么定验收指标。注意事项：机器学习的效果上限由数据决定，规律不在数据里，再好的算法也学不出来；立项时先确认数据够不够、标注质量如何，别等模型训完才发现它学的是错误规律。

### **SFT 指令微调（Supervised Fine-Tuning, SFT）：**

SFT 即监督微调，是大模型训练的第二个阶段：预训练让模型读完海量文本学会语言，SFT 则用人工整理好的「指令—回答」样本，教它听懂指令、按要求做事。样本通常是成对的提问与理想回答，模型拿它们继续训练，学会该怎么答、答成什么格式、用什么口吻。我们日常用的对话模型基本都经过这一关：它决定了模型「会不会做事」，而 RLHF、DPO 决定的是「做得讨不讨人喜欢」。PM 筹备微调项目时，SFT 是最先要过的方案：要固化话术、格式、分类口径这类「照着样例学」的行为，就准备高质量指令数据做 SFT，并先小批量验证数据质量，再扩大规模。注意事项：SFT 的效果天花板就是样本质量，标注口径不一致、答案本身有错，模型会学得一本正经地错；它教的是行为模式，灌新知识的效率低，知识更新仍要靠 RAG。

### **温度与采样参数（Temperature & Top-p）：**

模型生成每个词时，面对的是一串候选词和各自的概率，到底挑哪一个，由采样参数说了算，其中最常用的是温度（Temperature）和 Top-p。温度像一个发散旋钮：调低，模型总挑概率最高的词，回答稳定、保守；调高，低概率的词也有机会被选，回答更发散、更有创意，也更容易胡说。Top-p 则是先圈定一个累计概率范围，只在这个小圈子里挑词，圈越小越稳。这是 PM 少数能亲手调的模型参数：制度问答、数据抽取这类要准的场景把温度压低，起名、写文案这类要花样的场景适当调高；同一个模型在不同功能里应该用不同取值，别全局一刀切。注意事项：参数只能调节随机性，治不了知识错误和幻觉，答错了先查检索和提示词，别指望调温度解决；调完必须在评测集上回归，凭手感调参是上线事故的常见来源。

### **Benchmark 基准测试（Benchmark）：**

Benchmark 是给模型用的标准化考试：一套固定的题目和判分规则，让不同模型在同一把尺子下比出高下，MMLU 等公开排行榜就是它的产物。它测的通常是知识、推理、代码、数学等通用能力，厂商发布新模型时晒的分数，绝大多数来自这类基准。它和企业自建评测集是两回事：基准测的是通用能力上限，自建集测的是在你自己的业务上到底行不行。PM 选型时可以把榜单当入围门槛：先用 Benchmark 筛掉明显不行的，再拿自家真实场景的评测集决选；面试被问「怎么判断一个模型好不好」，答「榜单看下限、业务集定胜负」就是完整的框架。注意事项：榜单分数会被「刷题」污染——题目可能已经混进训练数据，分数虚高；也要警惕只挑对自己有利的榜单来宣传，关键结论永远以自家评测集的实测为准。

### **可观测性与链路追踪（Observability & Tracing）：**

AI 应用出了问题不能靠猜：可观测性就是给系统装上仪表盘，把每次请求的输入、输出、耗时、成本和中间步骤都记录下来，随时可查。其中链路追踪专管 Agent 和 RAG 这类多步链路：一次提问经过了哪几步检索、调了哪个工具、每步花了多久、哪一步开始出错，都能串成一条链完整回放。LangSmith 这类工具就是专门做这件事的平台，在 LangChain 生态里尤其常见。PM 要把可观测当成上线门槛，而不是事后补课：没有链路记录，Badcase 来了只能干瞪眼；需求阶段就该定清要记录哪些字段、盯哪些指标（失败率、P99 延迟、单次成本），并纳入验收。注意事项：日志里会留存用户的输入和模型的输出，涉及隐私与敏感数据，要做脱敏和留存期限管理；另外监控要设报警阈值，只记录不看，等于没装。
