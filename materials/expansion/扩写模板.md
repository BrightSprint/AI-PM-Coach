# 扩写模板 — 从 50 题扩写版提炼（对其余 497 题同标准扩写）

> 提炼自《AI 产品经理面试 · 大白话详解版（50 题全解）》（expanded-50.md）。
> 50 题实测：每题中位约 2800 字（高频 RAG 题 3500-9300 字），是原回答思路的 3-5 倍。
> 扩写 = 不是把原答案写长，而是每题固定补齐下面 5 个面 + 全篇共用 1 块项目背景板和 1 本数字账本。

## 一、全篇层（只写一次，所有题共用）

### 1. 主线项目背景板：HR AI 助手「小像」
- 约 100 人公司、企业微信入口、2026 年 10 月上线；GitHub 开源 BrightSprint/HR-AI-Agent（开源版为脱敏演示数据，内部实例接真实知识库）
- 用户：HR + 全体员工；场景：制度问答（婚假/社保/合同续签等）→ 标注引用来源、可点开核实
- 链路：员工提问 → 意图识别 → Query 改写（小模型，含多轮补全）→ 多路检索（向量 + BM25 + HyDE）→ RRF 融合 → 重排精选 Top5 → 大模型生成 + 引用溯源
- 技术栈：Coze + LangGraph/LangChain 编排 6 大工作流（约 45 节点）；GLM-4-Flash 做改写等轻量任务、GLM-4 生成；Redis 做改写缓存；向量库/HNSW 等底层按「规模增长后的演进选项」讲，不冒充已上线
- 知识库：约 60 份制度文档（假期/考勤/社保/合同等），章节语义切块，每块带元数据（文档类型、生效日期、适用地域）
- 7 项核心指标：recall@20、问答率、幻觉率、P99 延迟、转人工率、办事成功率、用户采纳率
- 上线门禁：21 条冒烟用例（9 类场景）+ 16 条上线检查单 + 四轮审查修复 28+ 处；意图双阈值 0.85/0.6；8 条安全红线；提示词版本化可回滚
- 演进路线：一期纯问答 → 二期办事 Agent（查资格 → 填 OA 请假单 → 4 级审批 → 材料补交/撤回 → 通知 → 回执）

### 2. 数字账本（全篇只能用这套数字，新扩写不许自创冲突数字；确需新数字先登记到这里并注明出处题号）
- 问答率 60% → 88%（归因：覆盖 +15pp / 召回 +8pp / 生成 +5pp）
- recall@20 70% → 85%（Multi-Query 改写 +8pp → 78%；BM25 混合检索 + RRF + 重排 +7pp → 85%）；检索侧 badcase 占 71%
- 幻觉率 8% → 2%（生成层：只基于资料回答 + 强制引用）
- P99 延迟 8.9s → 4.3s（目标 <5s）
- 评测集 500 → 900 条滚动增长；标注一致性 71% → 93%
- 办事 Agent 端到端成功率 89% → 97%；请假类工单 -64%；HR 月省 60 工时
- 冷启动：MVP 两周 Wizard-of-Oz 验证，61% 代办意愿；首月采纳率 61% → 79%
- 成本：以代码块代替模型环节，token 成本压降 30-45%
- 知识库：约 60 份文档；检索粗筛 Top20 → 重排精选 Top5；RRF k=60；改写 4 路表述 + 1 路关键词

## 二、单题层：固定五段式（每题必备，顺序不变）

### 一、这题在问什么
- 点破面试官真实意图（想确认什么经历/能力，最怕听到什么答法）
- 给出「黄金答题框架」一句话：本题的总结构（如「沿链路分层优化」），先框架后细节

### 二、参考答案大白话拆解
- 把原题库的回答思路逐点展开成大白话：每个要点讲清「是什么 → 为什么 → 怎么做」
- 补工程细节（参数、阈值、兜底、成本意识）——说出细节才显得真做过
- 保留原框架的关键词和顺序，不另起炉灶、不编造原文没有的专有方法论

### 三、实机案例：小像的××（起一个故事名，如「编假条事故」「切香肠事故」「P99 8.9 秒定位战」）
- 必须是小像项目内的具体事件：当时出了什么问题/处于什么阶段 → 做了什么动作 → 结果如何
- 有数字时用「动作前 → 动作后 → 归因」账本式呈现（表格或三段式），数字只能取自数字账本
- 题目与问答链路无关时（方法论/行业/软素质题），案例挂到项目对应阶段（如 MVP 冷启动、上线门禁、说服业务方用 88% 之争），不硬套技术链路
- 项目确实没做过的：按心法写「这个我们没上，但判断是……」，或标注为演进选项，不冒充已上线

### 四、新手常见的坑
- 2-3 个，具体到错误答法原话级别（如「只背名词不讲归因」「用生成层去救召回的锅」「改写时加幻觉」）
- 每个坑点出为什么扣分

### 五、追问预案 + 一句话总结
- 2-3 个面试官最高概率追问，每个给答法要点（可直接背的口径）
- 最后一句「一句话总结」金句收尾
- （可选，仅高频核心题）追问深挖：对 1-2 个最硬的技术点做实机级展开（原理 + 小像的参数/做法），如 BM25 打分、RRF、recall@ 计算、双阈值

## 三、写法规则（质量红线）
1. 大白话优先：术语出现时立刻跟一句人话解释（如 Cross-Encoder = 把问题和文档拼在一起逐字比对，慢但准）
2. 答题三板斧贯穿全篇：先框架 → 每个论点挂案例 → 收尾报数字 + 一句总结
3. 数字一致性：与数字账本冲突的表述一律改掉；新题需要新数字时，先在该题 check 文件中申报，汇总后登记进账本再继续下一批
4. 案例不重复：同一故事（如问答率 60→88 账本）可被多题引用，但每题的实机案例主体事件不得与已扩写题目雷同，要从项目不同侧面取材（清洗、评测、延迟、安全、审批流、冷启动等）
5. 分类组织：扩写版按主题分类编排（RAG 与知识库 / Agent 与智能体 / 大模型技术基础 / 产品经理方法论 / AI 行业认知，后续可增补：数据与评测、项目管理与软素质、HR 与职业规划、概念详解），不按原题库章节顺序；每题保留与原题库的对应编号（全局号 G + 章内号）以便回溯
6. 长度：普通题 2200-3200 字；类别内最高频的题 3500 字以上并配追问深挖；不为凑字数注水
7. 标题格式沿用扩写版：`## 第 N 题｜短标题` + `**题目**：原题面（白话微调可，但须可回溯原题）`
